# 온답 핵심 추천 엔진 재설계안

작성일: 2026-11-01. 상태: 개발 착수용 제안, 운영 승인·특허 일치 검증 완료를 뜻하지 않는다.

## 1. 이번 작업의 목표

고객의 행사 조건으로 부적절한 상품을 제외하고, 남은 상품에 별도의 추천점수를 계산하여 최대 3개를 제시한다. 관리자는 기존 상품 자료와 5대 희소 속성만 검토한다. 고객 결과·관리자 검증·문서 생성은 동일한 엔진의 동일한 결과를 사용한다.

자연어 고객 입력은 구현하지 않는다. 상품 지표 v1 화면·점수·가중치·미검수 상품으로 되돌아가는 경로는 만들지 않는다. 이번 턴은 설계와 작업 분담 문서 작성이며 운영 코드를 변경하거나 배포하지 않는다.

## 2. 핵심 범위와 보류 범위

이번 범위:
- 구조화 입력: 행사, 받는 분과 관계, 예산 방식(개당/전체/없음), 수량. 기존 링크 유지.
- 상품 데이터: 상품번호, 상품명, 판매가, 진열/판매/품절 상태, 이미지와 쇼핑몰 URL. 카페24를 원본으로 사용한다.
- 관리자: 상품 원자료 확인 → AI 제안 검토 또는 직접 수정 → 5대 속성 검수·저장.
- 행사 격식값과 상품 희소값을 비교하는 1차 적격 판정.
- 행사 적합도와 가격 실속으로 별도 추천점수 계산, 최대 3개 출력.
- 계산 내역, 제외 사유, 평가 근거 수, 정책 버전 확인.
- 추천 결과와 선택 상품·수량·예산을 포장 및 로컬 결재 문서에 일관되게 전달.

보류:
- 고객 자연어 분석, 트렌드·계절·리뷰·커스터마이징 점수, 자동 학습.
- 실제 재고 수량, 제작기간, 배송 도착일 확약, 최소/최대 주문량의 상세 매칭.
- 카테고리 선호 입력과 다양성 점수. 현재 카페24 수집 모델에 분류가 없으므로 분류를 추측하거나 관리자에게 다시 입력시키지 않는다.
- 발신 주체·행사 목적의 신규 필수 입력. 이미 받은 실제 값만 쓰며, 미입력은 unknown/0 보정으로 처리한다.
- 결재 문서 운영 공개, 주문·결제 재설계, 포장 에디터 재개편.

보류 항목은 데이터가 실제 확보된 시점에 별도 작은 변경으로 추가한다. 사용하지 않는 확장 슬롯·추정 점수·기본값을 미리 만들지 않는다.

## 3. 반드시 구분할 세 값

| 값 | 입력 | 의미 | 역할 |
| --- | --- | --- | --- |
| 행사 격식값 F | 행사·관계와 실제 전달된 추가 조건 | 행사 쪽 요구 수준 | 허용 희소구간과 2차 적합도의 기준 |
| 상품 희소값 R | 검수한 5대 속성 | 상품 쪽 평가 | 1차 기준 통과 및 2차 거리 비교 |
| 추천점수 S | 통과 상품의 행사 적합도와 가격 실속 | 현재 고객 조건에서 비교한 값 | 최종 순위 |

F, R, S를 같은 필드에 복사하지 않는다. 변수·화면·로그·문서에서 각각 이름을 유지한다. S를 품질 인증, 법적 적합, 구매 전환 확률로 설명하지 않는다.

## 4. 상품 희소 평가

속성은 생산자 숙련도, 지역적 희소성, 유통 제한성, 역사성, 지역 스토리의 5개다.

현재 세 단계 선택을 반드시 2/5/8점으로 변환하는 방식은 신규 평가에서 종료한다. 새 평가값은 속성별 0~10점(이번에는 정수)과 확인 근거를 함께 저장한다. 숫자 선택지를 늘리는 것만으로 평가가 객관화됐다고 간주하지 않는다.

관리자 부담:
- 원자료가 있으면 기존 AI 제안 기능을 이용하되 점수·근거는 제안 상태로만 보여 준다.
- 관리자가 내용을 확인해 검수를 완료한다. 직접 수정은 같은 카드에서 한다.
- 산지·분류·신뢰·안전·실용성의 추가 점수 입력은 없다.
- 외부 이미지뿐인 상세설명, AI 오류, 근거 부족은 직접 원자료 보완으로 처리한다. 새 OCR 개발은 보류한다.

새 평가 기준표 초안은 각 속성에 0/2/5/8/10의 설명과 사례를 작성하고 중간 정수의 사용 조건을 정한다. 경력 연수·자격 보유 등을 임의로 객관적 점수로 단정하지 않는다. 실제 상품 몇 건을 사람이 비교 평가한 후 기준표를 확정한다. 이 검증은 Codex가 문서화하고 운영 전환 전에 결과를 보고한다.

검토할 기준표의 방향은 아래와 같다. 확정된 특허 기준이 아니라 평가 기준 작성의 출발점이다.

| 속성 | 낮은 수준의 확인 사례 | 중간 수준의 확인 사례 | 높은 수준의 확인 사례 |
| --- | --- | --- | --- |
| 생산자 숙련도 | 일반 생산 공정이라는 자료 | 지속된 전문 생산 경험 | 전승·숙련·성과가 구체적인 자료로 확인됨 |
| 지역적 희소성 | 여러 지역에서 보편 생산 | 특정 산지의 생산 특징 | 생산 가능한 산지·생산자가 매우 제한됨 |
| 유통 제한성 | 상시 대량 공급·광범위 유통 | 일부 판매처·계절 공급 | 한정 생산량·유통 범위가 실제 수치로 확인됨 |
| 역사성 | 보편적인 현대 제조 방식 | 일정 기간 유지된 제조 이력 | 긴 전승 이력과 현재 제조 방식의 연결이 확인됨 |
| 지역 스토리 | 상품과 지역의 연계가 약하다고 확인 | 구체적인 지역 연결 | 지역 문화·장소와 상품의 직접적 연결 근거가 충분함 |

자료가 없는 경우는 낮은 점수 사례가 아니라 미평가다. 중간 정수는 어느 기준 사이에 해당하는지 설명할 수 있을 때 사용한다. 인증·수상 이름이나 오래된 연혁 한 가지만으로 최고점을 자동 부여하지 않는다. 숫자의 다양성을 위해 랜덤 점수나 설명되지 않는 소수점을 쓰지 않는다.

R = 10 × Σ(속성점수 × 속성가중치) / Σ(평가에 사용한 가중치)

- 근거가 있는 입력만 사용한다. 미입력과 확인된 0점을 구분한다.
- 근거 없는 항목을 자동 0점이나 평균으로 채우지 않는다.
- 사용한 속성 수/5를 별도로 반환한다. R이 같아도 근거 범위가 같다고 설명하지 않는다.
- 최소 유효 속성 2개는 현행 호환을 위한 초기 정책이며 검증된 특허 요구라고 단정하지 않는다. 정책과 검증 화면에 명시한다.
- 전부 8점이면 R=80인 것은 평균 산식상 정상이다. 목표는 모든 상품을 억지로 다른 점수로 만드는 것이 아니라 근거가 다른 평가를 표현하는 것이다.

기존 자료 보존:
- 기존 level/basis 자료를 삭제하거나 점수를 확대 환산하지 않는다.
- 기존 low/medium/high는 읽을 때만 2/5/8로 해석하며 평가 방법을 legacy-level로 표시한다.
- 새 저장에는 score/basis와 평가 기준 버전을 사용한다. 과거 평가가 새 기준으로 재검수됐다고 표시하지 않는다.
- 수정은 검수 해제를 거쳐 저장한다. AI가 기존 검수 자료를 자동 덮어쓰지 않는다.

## 5. 1차 필터: 추천 가능한가

순서:
1. 상품번호·가격 등 필수 데이터의 형식 검증.
2. 판매/진열 중이며 품절이 아닌가.
3. 고객이 제외한 상품이 아닌가.
4. v2 검수 완료 및 최소 유효 근거를 갖췄는가.
5. 행사·관계로 F를 계산하고, 정책 구간에 따라 R이 허용 범위에 속하는가.
6. 실제 예산이 있으면 상품비가 한도를 넘지 않는가.

유효한 기존 v2 행사 제외 규칙이 있으면 보존하고 적용한다. v1 제외 규칙을 조용히 가져오지 않는다. 새로운 정교한 행사 금기 분류나 운영 입력을 이번에 확대하지 않는다.

모든 탈락은 코드와 사람이 읽을 사유를 반환한다. 기준을 자동 완화하지 않는다. 후보가 0/1/2개면 그대로 표시한다. 정확한 재고 수량·납기까지 확인했다고 표시하지 않는다.

예산:
- 전체 예산 T, 수량 Q가 있으면 직접 P×Q≤T로 판정한다. 1개당 한도는 표시·비교용으로만 floor(T/Q)를 쓴다.
- floor(T/Q)=0이면 예산 없음으로 바꾸지 않는다. 양수 판매가 상품은 모두 예산 초과다.
- 개당 예산 B는 P≤B로 판정한다.
- 배송·옵션·포장 추가비를 상품비 예산 적합 판단에 몰래 포함하거나 확정 총액이라고 표시하지 않는다.
- 예산 없음과 잘못된 예산 입력을 구분한다.

## 6. 2차 평가: 무엇을 먼저 추천하는가

초기 정책 제안이다. 출원서가 이 수식·가중치를 지정했다고 주장하지 않는다. 실제 비교 시나리오와 담당자 검토를 통과하기 전 운영 정책으로 확정하지 않는다.

추가 상품 입력이 없는 두 항목으로 시작한다.

### 행사 적합도 E

E = max(0, 100 - |R - F|)

1차 필터는 범위 밖 상품을 제외하고, E는 통과 상품 중 행사 요구 수준과 가까운 정도를 표현한다. 같은 희소값도 행사 조건이 달라지면 E가 달라질 수 있다. 이는 초기 거리 기반 매칭 정책이다. 희소값이 항상 높을수록 좋은 순위가 되는 방식은 아니다.

### 가격 실속 V

예산이 있을 때 V = 100 × (1 - 상품비 / 예산).

개당 예산은 P/B, 전체 예산은 (P×Q)/T를 사용한다. 적격 판정을 통과한 상품만 계산하므로 0~100 범위다. 이것은 저렴할수록 높아지는 가격 실속이며 상품의 품질·가치 평가가 아니다. 예산 상한에 가까운 상품이 유리한 ‘예산 활용도’와 혼동하지 않는다.

### 종합 추천점수 S

예산이 있으면 S = (70×E + 30×V) / 100.
예산이 없으면 V는 null이며 S=E. 미입력 가격 점수를 0이나 100으로 채우지 않는다.

70/30은 검토용 초기 제안이다. 별도 수동 상품점수는 만들지 않는다. 정책 화면에서 E/V 비중과 산식 설명을 함께 관리하며 저장은 서버에서 검증한다.

계산 예시(F=80, 개당 예산 50,000원, 모두 1차 통과):

| 상품 | R | 단가 | E | V | S |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 80 | 22,000 | 100 | 56 | 86.8 |
| B | 90 | 18,000 | 90 | 64 | 82.2 |
| C | 75 | 30,000 | 95 | 40 | 78.5 |

A는 B보다 비싸지만 행사 적합도가 높아 앞선다. 이것으로 ‘그냥 가격순’과 다른지 검증한다. 같은 입력값이면 같은 점수·순서가 나와야 하며, 동일한 점수가 나올 수 있는 것은 허용한다.

정렬: 반올림 전 S 내림차순 → E 내림차순 → 판매가 오름차순 → 상품번호 오름차순. 화면에만 소수 첫째 자리 반올림. 임의 난수나 설명용 가산점은 없다. 최대 3개, 선택지 역할은 추천 1/2/3위이며 실속/표준/격식 세트로 꾸며 말하지 않는다.

## 7. 화면

고객:
- 기존 행사·관계·예산·수량 폼을 유지한다. 새 필수 입력을 추가하지 않는다.
- 대표 숫자는 ‘추천점수 S’. 상세에서 ‘행사 적합도 E / 가격 실속 V / 상품 희소값 R’을 구분한다.
- 예산 없음은 V를 ‘미평가(예산 미입력)’로 표시한다.
- 0/1/2/3개 후보를 모두 정상 상태로 지원한다. 제한이 실제 원인과 맞는 안내를 한다.
- 필터 결과를 품질 인증처럼 표현하지 않는다. 추천 사유는 반환된 계산 근거로 작성하며 순위에 영향을 주지 않는다.

관리자:
- ‘격식지수 판정’만 사용한다. v1 경로·쓰기 차단 유지.
- 5대 속성 카드에서 AI 제안·확인 근거·0~10점·미입력·검수 상태를 다룬다.
- 검증실과 알고리즘 검증은 같은 엔진 출력을 표시한다. 별도 산식 금지.
- 정책 화면은 행사 기준·희소 가중치·추천점수 E/V 가중치만 다룬다.
- 과거 수준형 평가에는 과거 방식 표시를 유지한다. 근거 수와 평가 기준 버전을 확인할 수 있다.

## 8. 공통 계약 core-contract-v1

Codex가 먼저 순수 타입 파일 src/recommendation/contracts.ts, UI fixture JSON, 짧은 사용 예제를 제공한다. 이것을 병행 작업의 시작 조건으로 한다. Antigravity는 계약 파일을 수정하거나 자체 계산식을 만들지 않는다.

계약상 핵심 필드:

```ts
type Budget =
  | { mode: 'none' }
  | { mode: 'per_item'; amount: number }
  | { mode: 'total'; amount: number };
type FactorAssessment = {
  score: number | null; // 0~10 정수, null은 미평가
  basis: string;
  method: 'legacy-level' | 'numeric';
  rubricVersion: string | null;
};
type RecommendationRequest = {
  event: string; relation: string; quantity: number;
  budget: Budget; excludedProductNos: number[];
};
type RecommendationItem = {
  productNo: number; name: string; unitPrice: number;
  imageUrl: string | null; productUrl: string;
  eventFormality: number; rarityValue: number;
  evidenceCount: number; assessmentMethod: 'legacy-level' | 'numeric' | 'mixed';
  eventFitScore: number; priceValueScore: number | null;
  recommendationScore: number;
  rank: number; reasons: string[];
};
type RecommendationResponse = {
  contractVersion: 'core-contract-v1'; policyVersion: string;
  request: RecommendationRequest;
  items: RecommendationItem[];
  exclusions: { productNo: number; code: string; message: string }[];
  notices: { code: string; message: string }[];
};
```

실제 필수 타입·행사 ID·API 형태는 Codex가 제공하는 타입 파일을 기준으로 한다. 문서의 발췌만 보고 UI에서 별도 느슨한 타입을 만들지 않는다.

필수 UI fixture: 후보 3개/1개/0개, 예산 없음, 과거 수준형 평가, 새 수치형 평가, AI 실패, 저장 충돌. 가상 자료임을 명시하고 운영 DB에 저장하지 않는다.

기존 rankScore/matchScore에 R을 대입하는 처리는 종료한다. 기존 호출부 호환이 필요하면 Codex의 단일 어댑터에서 변환하고, UI의 필드 이름 변경으로 계산 오류를 숨기지 않는다.

## 9. 저장과 이관

- 기존 product_evidence의 속성 JSON에 새 score/basis를 저장하는 최소 변경을 우선 검토한다. 새 테이블이 반드시 필요한지 먼저 판단한다.
- 기존 level/basis와 새 score/basis를 구분한다. 조회나 정책 저장만으로 상품 평가 자료를 덮어쓰지 않는다.
- 검수 해제·저장 실패·AI 오류에서 기존 기록과 입력을 보존한다.
- 동일 상품 동시 저장은 updatedAt 등 기대값을 검사해 충돌을 알린다. 필요한 DB 변경은 Codex가 담당한다.
- 공개 응답에는 원자료·관리자 식별자·서비스 키를 넣지 않는다.
- 조건·정책·평가기준·계산 결과의 버전을 기록하고 로그와 결재 사본에서 당시 R과 S를 구분한다.

## 11. 진행 순서

0. Codex가 공통 타입·fixture·짧은 사용 예제와 서버 호출 서명을 먼저 고정한다. 병행 개발의 시작 조건이다.
1. 병행: Codex는 엔진/저장/어댑터, 안티그래비티는 fixture 기반 UI를 개발한다.
2. 실제 서버 함수가 준비되면 안티그래비티가 지정된 함수에 연결한다. 임시 데이터 생성기는 UI 테스트 외에 남기지 않는다.
3. 안티그래비티는 변경 패치/커밋과 검증 보고서를 제출한다. 운영에 직접 push/deploy하지 않는다.
4. Codex가 변경 내용 검토, 실제 브라우저, 계산 결과 일치, 기존 연결을 검증하고 통합한다.
5. 실제 상품 평가 사례와 추천 비교를 보고해 초기 정책을 확인한다. 실패·미검증 항목이 있으면 구분해서 보고한다.
6. 이 설계안 작성 자체로 운영을 변경하지 않는다. 통합 검증 결과 보고 후 사용자 최신 지시에 맞춰 반영한다.

## 12. 완료 기준

- R과 S를 별개 값으로 API·고객 화면·관리자·로그·문서에서 확인할 수 있다.
- 구조화 입력 → 1차 적격 판정 → 2차 추천점수 → 최대 3개 결과가 같은 엔진으로 동작한다.
- 같은 R이어도 가격/예산이 다르면 S가 달라지고, 같은 가격이어도 F/R 관계가 다르면 S가 달라진다. 실제 값이 같으면 같은 점수를 허용한다.
- 가격이 가장 저렴한 상품이 항상 1위가 되지 않는 검증 사례를 갖춘다.
- 전체/개당/미입력 예산, 개당 한도 0, 확인된 0점과 미입력, 근거 2개/5개, 과거 자료, 고객 제외를 확인한다.
- 기준 탈락 상품을 2차 점수로 되살리지 않는다. 부족한 후보를 v1 상품으로 채우지 않는다.
- 고객 결과와 관리자 검증, Word/PDF/HWPX의 상품 및 R/S 의미가 일치한다. 로컬 문서를 운영 공개하지 않는다.
- 실제 브라우저로 저장→재조회, 과거 평가 수정, AI 실패, 결과→포장의 상품/수량 유지, 모바일 375px 및 PC를 확인한다.
- test/typecheck/build와 변경에 맞는 실제 E2E를 실행한다. HTTP200이나 코드 문자열 검색만으로 조작 성공을 보고하지 않는다.

## 13. 알려진 한계

이 초기안은 구조도의 두 단계 매칭을 핵심으로 구현하는 제안이며, 구조도의 모든 다차원 항목을 구현하는 것은 아니다. 특허 원문과의 일치, 실제 평가의 타당성, E/V의 70/30 비중은 미확정이며 각각 검증해야 한다. 빠진 데이터를 새 관리자 입력과 근거 없는 점수로 채우지 않는다.
