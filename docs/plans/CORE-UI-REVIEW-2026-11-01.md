# 안티그래비티 UI 커밋 검토

검토일: 2026-11-01. 대상: C:/Users/xshon/Desktop/ondapmvp-core-ui, antigravity/core-ui, 1b37cad.
판정: UI 초안은 준비됐지만 현재 상태로 통합·배포하지 않는다. 아래 문제를 수정하고 실제 서버와 함께 검증해야 한다.

## 확인한 정상 범위

- 공통 contracts.ts / evaluate.ts / validation.ts 변경 없음.
- UI는 src/app/recommendation-ui에 분리되어 있으며 실제 고객/관리자 화면에는 아직 연결하지 않았다. 이는 초기 소유권 지시와 일치한다.
- S/E/V/R 분리 표시, V=null의 미평가 표시, 후보 개수 가변 표현은 구현되어 있다.
- npm test를 다시 실행해 226개 통과를 확인했다. npm run typecheck도 통과했다.
- next build --webpack 재실행 통과. 빌드된 로컬 production 서버에서 /recommendation-ui의 HTTP 404도 실측했다. 검토를 위해 시작한 3320번 서버는 종료했다.
- 실제 Chrome에서 3320번 개발 프리뷰를 열고 아래 두 결함을 직접 재현했다. 기존 3000번 서버는 건드리지 않았다.
- 검토 과정에서 안티그래비티 소스와 저장 데이터는 수정하지 않았다. 브라우저에서 바꾼 값은 가상 서비스의 메모리 안에만 존재한다.

## 통합 전에 반드시 수정

### 1. 새 조건과 이전 추천 결과가 섞여 잘못된 금액이 표시됨 [P1]

위치: customer-view.tsx:39,45,64,82,222.

실제 재현: 기본 10개 결과 → 저장 실패 시뮬레이션 활성 → 조건 바꾸기 → 수량 100개 → 추천 요청.
요청 실패 후 헤더는 100개지만 22,000원 상품의 합계는 이전 10개 금액인 220,000원이다. 포장 링크는 qty=100으로 열린다.

원인: 요청 조건을 먼저 바꾸고 response는 성공할 때만 교체한다. 카드·링크는 새 request를, 금액·점수는 이전 response를 사용한다. 늦게 도착한 과거 요청을 버리는 처리도 없다.
수정: 입력 초안과 마지막으로 성공한 응답을 구분하고 상품·합계·링크는 같은 response.request에서 만든다. 새 요청 중/실패 시 과거 결과를 현재 결과처럼 사용할 수 없게 한다. 최신 요청만 반영하고 실패 시 입력·재시도를 제공한다.

증거: ../screenshots/core-ui-review-request-mismatch.png.

### 2. 상품 전환 시 관리자 입력 유실 및 늦은 응답의 상품 혼입 [P1]

위치: admin-workbench.tsx:29,54,159,180,221,335.

실제 재현: 900001의 생산자 숙련도 근거를 '[검증용] 저장하지 않은 근거'로 수정 → 900002 선택 → 다시 900001 선택. 확인창 없이 원래 근거로 돌아간다. dirty 상태는 상품 전환에 사용되지 않는다.
AI/저장 도중에도 상품 전환·근거 수정이 가능하며 응답은 요청 당시 draft를 그대로 setDraft한다. 느린 A 상품의 응답이 B 상품 헤더 아래에 들어가거나 요청 후 입력이 사라질 수 있다.

수정: 상품별 작성 중 내용을 보관하거나 명시적인 버리기 확인을 제공한다. 상품번호·요청 순서·편집 세대가 같은 응답만 반영하고, 저장/AI 처리 중 수정도 유실되지 않도록 한다.

### 3. 충돌 해결이 실제 서버 계약과 다름 [P1]

위치: admin-workbench.tsx:191,199,237,600; admin-weights-editor.tsx:62,68,125; mock-services.ts:139,233.

두 편집기에 '내 내용/내 설정으로 덮어쓰기'가 있으며 expectedUpdatedAt을 null로 보낸다. null은 신규 생성 기대값이지 충돌 우회 옵션이 아니다.
실제 서버는 기존 자료가 있으면 충돌로 거부한다. 반면 모의 서비스는 null 비교를 생략하므로 기존 자료를 덮어쓴다. 직접 호출로 mockOverwritesExistingWithNull=true를 재현했다.
또한 평가 '최신 자료로 새로고침'은 draft만 갱신하고 workspace.assessments는 갱신하지 않는다. 다음 저장은 workspace의 과거 시각을 사용하여 다시 충돌한다. 최신 자료 호출은 현재 입력도 즉시 버린다.

수정: 강제 덮어쓰기 경로를 삭제한다. 현재 입력을 보존한 상태로 최신 자료와 비교하고, 사용자가 재적용한 뒤 최신 updatedAt으로 다시 저장하게 한다. 조회 기준과 편집 초안의 개정을 함께 관리한다.

### 4. AI 제안이 기존 근거를 지우며 원자료를 확인할 입력도 없음 [P1]

위치: admin-workbench.tsx:69,131,159,168.

실제 서버의 제안은 5개 속성 객체를 모두 반환하며 미확인은 score=null이다. UI는 객체가 존재하는지만 확인하고 전부 교체한다. 따라서 skill만 제안된 경우에도 기존 나머지 4개 근거가 빈 값으로 사라진다. 현재 mock은 언제나 5개 속성의 점수를 만들어 이 반례를 가린다.
원자료 description을 표시·편집하는 곳이 없어서 새 상품은 상품명만 AI에 보내게 된다. 상품명으로 전승·생산량·역사성을 확인할 수는 없다.
과거 평가에서 근거 문장만 수정해도 점수는 그대로 둔 채 method를 numeric으로 바꾼다. 실제 수치 재평가 없이 새 기준 평가로 표시되는 문제다.

수정: 원자료를 확인할 수 있게 하고 부족하면 분석을 요청하지 않는다. 제안된 유효 속성만 검토·적용하며 미확인 제안으로 기존 값을 지우지 않는다. 과거 근거 문장 편집과 새로운 수치 점수 판정을 구분한다.

### 5. 화면 이동·공유에 현재 조건이 보존되지 않음 [P2]

위치: customer-view.tsx:82,268,293; 기존 packaging/page.tsx:38.

실제 전체 예산 500,000원/10개 시나리오의 포장 링크는 budget=500000만 담고 budgetMode/totalBudget이 없다. 포장 페이지의 돌아가기 링크도 전체 예산 메타데이터를 보존하지 않는다. 이후 결과 화면에서는 개당 예산으로 해석된다.
공유는 조건을 바꿔도 갱신되지 않는 window.location.href를 복사한다.
결재 링크는 존재하지 않는 /approval?event=...로 이동한다. 기존 결재 흐름은 POST 초안 생성 후 /approval/[id]이며 URL 이동만으로 생성되지 않는다.

수정: Codex 공통 URL 도우미로 성공 응답의 조건을 직렬화한다. 결재는 기존 가드와 실제 생성 흐름에 연결하기 전까지 성공하는 버튼처럼 표시하지 않는다. 기존 포장 호출부·결재 어댑터의 최종 연결은 Codex 담당이다.

### 6. 배송비 기준을 새로 하드코딩함 [P2]

위치: pick-cards.tsx:25,245.

5만 원 미만 배송비를 3,000원으로 새로 계산하지만 기존 공통 shippingFee는 2,500원이다. 상품 합계 22,000원일 때 서로 다른 예상 합계가 나온다.
수정: 공통 배송비 도우미를 재사용하고 기존 단일 배송지 참고 기준 안내를 유지한다. UI에서 별도 배송 정책을 만들지 않는다.

### 7. 초기 조회 실패·검증실 오류가 숨겨짐 [P2]

위치: admin-workbench.tsx:43; admin-weights-editor.tsx:46; admin-verify-view.tsx:39,54,61.

작업공간/정책 조회가 unauthorized 또는 unavailable이면 오류·재시도 없이 로딩 문구만 남는다. 통신 예외 처리도 없다.
검증실은 실패 응답을 생략하고 성공한 셀만 집계한다. 예산을 연속 변경하면 이전 실행의 결과가 새 예산 밑에 늦게 표시될 수 있다. 32회 서버 호출을 순차 실행하므로 실제 서버에서는 매번 카탈로그/평가를 반복 조회한다.
수정: 조회·셀별 실패를 빈 후보와 구분하고 재시도를 제공한다. 최신 실행만 반영하고 검증 범위/성공/실패 개수를 표시한다. 일괄 시험용 공통 서버 연결은 Codex와 조정한다.

### 8. 모의 서비스와 테스트가 실제 UI 결함을 잡지 못함 [P2]

위치: mock-services.ts:124,220; test/recommendation-ui.test.ts:9,188,300; finder-form.tsx:53; admin-weights-editor.tsx:216.

직접 검증: mockSavesInvalidMinimum=true, realParserAcceptsInvalidMinimum=false. 정책 UI는 최소 근거 1개를 허용하지만 공통 파서는 2개 이상만 허용한다. UI 수량 상한 5,000도 계약 상한 100,000과 다르다.
'작성 내용 보존' 테스트는 실제 React 편집기를 조작하지 않고 테스트에 만든 객체가 변하지 않았는지만 확인한다. 포장 링크 테스트는 실제 packagingHref를 사용하지 않고 테스트 안에서 URL을 다시 만든다. '같은 희소값의 다른 추천점수' 테스트도 실제 R이 같은지 확인하지 않는다.

수정: 모의 저장도 공통 파서와 동일한 null/개정 규칙을 따른다. 실제 컴포넌트의 입력→요청→실패/복구→화면/링크 흐름으로 재현 가능한 테스트를 추가한다. HTTP200·스크린샷 생성·함수 단위 테스트를 실제 UI 상태 전이 검증으로 보고하지 않는다.

## 통합 상태와 미검증

아직 UI를 Codex 브랜치에 합치지 않았다. 운영 push/deploy/DB 쓰기는 없다. 운영 전 실제 Supabase 인증·충돌·추천 결과·결재 사본·공유·포장 왕복을 추가 검증해야 한다.
서버는 운영 배포 없이도 로컬에서 연결할 수 있다. Codex의 a383d10에 server.ts와 실제 로컬 저장 구현이 있다. '서버를 배포해야 UI 연결 가능'하다는 설명은 정확하지 않다.
