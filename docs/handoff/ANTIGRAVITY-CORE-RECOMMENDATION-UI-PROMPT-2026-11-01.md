## 배경과 목표

현재 구현은 상품 희소값과 추천점수의 의미가 섞였고, 잘못 추가한 관리자 입력 및 점수 계산의 반복 변경으로 고객 추천이 혼란스러워졌다. 이번에는 아래 흐름을 UI에 정확히 반영한다.

고객 구조화 입력 → 행사 기준과 상품 희소값으로 1차 판정 → 통과 상품의 행사 적합도·가격 실속을 별도로 평가 → 종합 추천점수로 최대 3개 표시.

너의 목표는 사용자가 이 계산을 쉽게 이해하도록 화면을 만드는 것이다. 점수 산식, 가중치, 필터, 기존 데이터 이관과 서버 저장은 Codex가 개발한다.

- 계약 파일을 받기 전에는 화면 배치·문구·컴포넌트 설계를 진행하라. 자체 타입/API/산식을 만들어 실행 가능한 척하지 마라.

## 고객 화면 요구사항

1. 기존 행사·관계·예산·수량 입력을 간결하게 유지한다. 새 필수 질문을 추가하지 않는다.
2. 예산은 개당/전체/없음을 구분한다. 전체 예산 원본을 보존하고, 수량 변경 시 새 요청으로 평가한다. UI에서 독자적으로 단가 한도를 계산하거나 전체 예산을 없애지 마라.
3. 대표 카드에는 추천점수 S와 상품명·가격·수량별 상품비·꾸미기 버튼을 제공한다.
4. 상세 설명은 행사 적합도 E, 가격 실속 V, 상품 희소값 R을 구분한다. 엔진이 준 결과와 사유만 표시한다.
5. 예산 없음이면 V는 ‘미평가(예산 미입력)’로 표시한다. 임의의 0점·100점으로 표시하지 마라.
6. 추천 0/1/2/3개에 맞게 제목·비교표·버튼을 표시한다. ‘무조건 추천 3개’ 같은 고정 문구 금지.
7. 후보 부족·예산 초과·미검수·자료 부족을 결과의 notice/exclusion 코드에 맞게 안내한다. 모든 실패를 ‘예산 확대’로 표시하지 마라.
8. 결재·공유 버튼은 부가 기능 위계로 유지한다. 결재 기능의 운영 가드를 UI에서 해제하지 마라.
9. 포장 이동 시 선택한 상품번호·수량·행사·관계·예산 조건을 Codex가 제공한 링크/계약대로 전달한다.
10. 정렬과 점수를 UI에서 재계산하지 않는다. 희소값을 추천점수 필드에 넣거나 이름만 바꾸지 마라.

## 관리자 화면 요구사항

1. 메뉴는 ‘격식지수 판정’이며 v1 화면·연결·저장 기능을 복원하지 않는다.
2. 산지·상품분류·신뢰안전·실용성 등 추가 추천 상품 정보 입력을 재도입하지 않는다.
3. 기존 5대 속성 카드 안에서 근거와 0~10 정수 점수를 검토한다. 점수 미입력과 확인된 0점을 명확히 구분한다.
4. AI는 제안이다. 점수·근거를 확인 후 저장하도록 하고, 기존 검수 자료를 자동으로 바꾸지 마라.
5. 관리자 확인 부담을 줄이기 위해 제안된 값은 한 화면에서 검토하고 필요한 값만 수정하게 한다. 불필요한 모달·추가 단계·장황한 안내를 만들지 마라.
6. 과거 low/medium/high 평가에는 과거 방식 표시를 한다. 기존 80점을 새로운 정밀 평가 80점으로 재검수된 것처럼 보이지 않게 하라. 표시 변환과 실제 저장을 구분하라.
7. 유효 근거 수/5, 검수 상태, 평가 기준 버전을 확인할 수 있게 하라. 개수로 임의 가산/감점하지 마라.
8. 저장 실패·AI 실패·동시 저장 충돌 시 입력을 보존하고 오류와 재시도 방법을 표시한다. 자동 재시도로 다른 관리자의 자료를 덮어쓰지 마라.
9. 가중치 설정은 서버가 제공한 행사 기준·희소 가중치·E/V 가중치만 편집한다. 기본값 70/30은 설계 제안이며 검증된 특허 산식이라고 설명하지 마라.
10. 알고리즘 검증과 격식 검증실은 같은 공통 결과를 사용한다. 운영 자료와 가상 시험 자료를 구분한다.

## 반드시 확인할 시나리오

- 동일한 희소값이지만 가격/예산이 달라 추천점수가 다른 두 상품 표시.
- 더 저렴한 상품보다 행사 적합도가 높은 상품이 앞서는 결과 표시.
- 예산 없음: V 미평가, S는 반환값 그대로 표시.
- 전체 예산과 수량 변경: 원래 전체 예산 보존.
- 추천 0/1/2/3개, 가격·근거 누락, 요청 실패·다시 시도.
- 과거 평가 불러오기 → 새 기준으로 수정 → 검수 해제 → 저장 → 재조회.
- AI 실패/저장 실패/저장 충돌에서 작성 내용 보존.
- 변경하지 않은 과거 평가를 열기만 해도 저장하거나 방식이 바뀌지 않는지.
- 결과 카드와 비교표·관리자 검증에 같은 상품·S/R/E/V 표시.
- 포장 링크에 상품·수량·행사 조건 유지.
- 375px 모바일/PC에서 표 잘림·입력창 겹침·버튼 접근성 확인.

화면 상호작용은 실제 브라우저로 검증하라. 함수 테스트·HTTP200·소스 문자열 확인만으로 UI 성공을 보고하지 마라.

## 제출물

1. 작업 브랜치와 변경 커밋 또는 적용 가능한 패치.
2. 변경한 파일 목록. 허용 영역 밖 변경은 별도로 명시.
3. 고객·관리자 핵심 화면의 PC/모바일 캡처.
4. 실제 수행한 검증 명령·결과와 브라우저 시나리오별 결과.

‘모두 정상’, ‘100% 일치’, ‘특허 준수’ 같은 포괄적인 완료 표현을 증거 없이 쓰지 마라. 테스트를 통과시키려고 기대값을 변경하거나 mock만 통과시키지 마라.
