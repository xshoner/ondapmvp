## 필수 보완

1. 고객의 입력 초안과 성공 응답 조건을 분리한다. 카드의 수량·금액·점수·포장/공유 링크는 같은 성공 응답에서 만들어야 한다. 요청 중/실패 상태에서는 이전 결과를 새 조건의 결과처럼 표시하거나 진행시키지 않는다. 역순 응답은 버리고 입력을 보존한 재시도를 제공한다.
2. 상품을 바꿔도 관리자 미저장 문구·점수가 유실되지 않게 한다. 상품별 초안을 보관하거나 버리기를 명시적으로 확인한다. AI/저장 응답은 상품번호와 편집 세대를 확인하여 다른 상품이나 더 최신 입력에 덮어쓰지 않는다.
3. 두 편집기의 '내 내용으로 덮어쓰기' 및 force/null 우회 경로를 삭제한다. 충돌 시 현재 입력을 보존하고 최신 자료를 별도로 확인한다. 재적용 후 최신 updatedAt으로 저장하며, 새로고침 후 또 과거 workspace 시각으로 저장하지 않게 한다.
4. AI의 미확인 null 속성으로 기존 점수·근거를 지우지 않는다. 원자료 description을 볼 수 있게 하고, 유효한 제안을 검토하여 적용한다. 상품명만으로 충분한 근거가 있는 것처럼 진행하지 않는다. 근거 문장 수정만으로 과거 평가를 새 수치 평가로 바꾸지 않는다.
5. 상품/정책 초기 조회 및 통신 예외를 오류·재시도 상태로 표시한다. 무한 로딩을 남기지 않는다. 검증실은 실행 순서와 셀별 실패를 관리하며, 실패를 후보 0개나 성공 검사에서 누락시키지 않는다. 의미 없는 요청 32회 반복을 서버 연결 전에 Codex와 조정한다.
6. 배송비는 기존 shippingFee를 재사용한다. 3,000원 하드코딩을 삭제한다. 입력 범위는 공통 파서와 일치시킨다(근거 최소 2, 수량 최대 100,000). UI에서 새 산식이나 범위를 만들지 않는다.
7. 공유는 실제 성공 조건을 담는 링크여야 한다. 전체 예산을 개당 예산으로 바꾸지 않는다. Codex query.ts 도우미를 사용할 연결 지점을 마련하고 존재하지 않는 /approval 링크는 제거한다. 결재 생성은 실제 흐름에 연결할 때만 제공한다.
8. 모의 저장은 공통 검증/충돌 규칙을 따른다. expectedUpdatedAt=null은 신규 저장 기대값이다. 기존 자료에 대한 강제 저장 허용값으로 해석하지 않는다. 테스트용 AI가 언제나 5개 속성을 지어내지 않게 하고 부분 제안·실패·지연 응답을 시험한다.

## 완료를 판단할 실제 시나리오

- 10개 정상 결과 → 100개로 변경 → 요청 실패: 이전 220,000원을 100개 금액으로 표시하지 않는다. 재시도 성공 후 수량·금액·링크 일치.
- A 요청을 느리게, B 요청을 빠르게 응답: 최종 화면과 진행 링크는 B만 유지.
- A 상품 근거 수정 → B 상품 → A 상품: 미저장 작성 내용 보존. 버리기는 명시적으로 선택할 때만.
- A AI 요청 → B 선택/입력 → A 응답: B의 화면/입력에 A 데이터가 들어가지 않음.
- 저장 요청 후 추가 입력: 응답 후에도 추가 입력 유실 없음.
- 실제 저장 충돌 → 내 작성 내용 보존 → 최신 자료 확인 → 재적용 → 최신 개정으로 저장 성공. 별도의 강제 덮어쓰기 없음.
- AI가 skill만 제안하고 나머지는 null: 나머지 기존 근거 보존. 과거 근거 문장만 수정해도 method가 임의 변경되지 않음.
- 전체 500,000원/10개 → 포장으로 전달할 링크/공유 링크에 원래 전체 예산 유지. 돌아가기 호출부 수정은 Codex에게 별도로 보고.
- 정책 최소 근거 1 입력 거부, 2/5 허용. 비어 있는 값과 0 구분.
- 관리자 조회 unauthorized/unavailable 및 검증실 일부 요청 실패: 오류·재시도·집계에 정확히 반영.

실제 UI 컴포넌트를 브라우저에서 조작하는 재현 스크립트와 실패 전/후 증거를 제출한다. 테스트 안에서 필터/URL을 재작성하거나 서비스 호출 전후에 상관없는 로컬 객체가 그대로인지만 확인하는 테스트로 대체하지 않는다.
