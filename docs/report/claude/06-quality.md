## [S-6] 6. 품질 검증 및 운영 점검

### [S-6.1] 검증 체계

○ 변경할 때마다 "자동 테스트 → 형식 검사 → 운영과 같은 방식의 빌드 → 화면 확인" 순서로 확인한 뒤에만 운영에 반영함
○ 운영에 반영한 뒤에는 운영 주소를 대상으로 점검 도구를 실행해 주요 화면과 보호 장치가 정상인지 확인함

| 검증 | 방법 | 확인하는 것 |
| --- | --- | --- |
| 자동 테스트 | `npm test` — 421개 항목 | 추천 계산, 격식지수 판정, 포장 데이터, 디자인 코드, 카페24 주문 연결·취소, 결재 문서 계산·출력, 보안 규칙 등 |
| 형식 검사 | `npm run typecheck` | 코드의 자료형이 서로 맞는지 (잘못된 값 전달 방지) |
| 운영 빌드 | `npm run build` | 운영 서버와 같은 방식으로 만들어지는지 |
| 화면 흐름 검증 | `npm run e2e` — 실제 브라우저 자동 조작 | 조건 입력 → 추천 → 포장 저장 → 쇼핑몰 도우미 → 관리자 처리까지 고객·관리자 흐름 |
| 데이터베이스 규칙 검증 | `npm run e2e:db` | 데이터베이스 변경 파일, 접근 규칙(RLS), 자동 처리(트리거) |
| 인쇄 파일 검증 | `npm run e2e:pdf` | 인쇄 PDF의 QR이 올바른 주소를 가리키는지 |
| 한글 문서 검증 | 한글 프로그램으로 결재 문서(HWPX)를 직접 열어 쪽 그림으로 확인 | 문단 간격, 표, 제목 배치가 화면과 같은지 |
| 운영 점검 | `npm run doctor -- https://dapcue.vercel.app` | 첫 화면·격식지수 소개·포장 화면·쇼핑몰 도우미·앱 정보 응답, 관리자 화면 로그인 보호 |
| 매일 자동 점검 | 매일 18:00 자동 작업 | 상품 동기화, 운영 상태, 임시 파일 정리 |

### [S-6.3] 보안 점검

○ 비밀 키(쇼핑몰 연동 키, AI 키 등)는 운영 서버의 보호된 환경 변수에만 저장하고 소스·문서에는 넣지 않음
○ 데이터베이스는 행 단위 접근 규칙으로 고객은 자기에게 필요한 최소 정보만, 관리자는 로그인 후에만 전체를 다루게 함
  - 고객의 디자인 코드 조회는 진행 상태·상품·수량만 돌려주고 편집 내용·주문번호·메모는 보여 주지 않음
  - 주문과 디자인을 잇는 기능은 검증된 서버에서만 실행되도록 제한함
○ 결재 문서는 만든 사람만 수정할 수 있게 하고, 다른 출처의 요청은 거절함
○ 사용 중인 웹 프레임워크(Next.js)의 보안 권고가 나오자 즉시 업데이트함 (2026-11-18)
