# 격식지수 v2: 엔진과 관리자 검증실

2026-10-28. 기존 v0.1 고객 추천은 유지한다. 이번 구현은 출원 구조의 순수 엔진, 가상 상품 3개, 관리자 검증 화면까지다. 운영 DB·결재 기능·주문 흐름은 바꾸지 않는다.

## 동작

1. 행사 유형·관계·발신 주체·목적으로 행사 격식 0~100 산출.
2. 상품마다 근거가 있는 5가지 희소 속성 평가값(0~10)을 0~1로 정규화하고 가중평균.
3. 해당 행사 구간의 희소 하한·상한을 충족하는지 먼저 판정.
4. 검수·근거 2개 이상·판매 가능·행사 금지·예산 조건을 통과한 상품만 가격 실속·신뢰·실용성으로 평가.
5. 순위와 카테고리 다양성으로 최대 3개 선택. 후보 부족 시 기준·예산을 자동 완화하지 않음.

출원서 청구항 1~5·7, ¶43~48·53~62의 처리 분리를 구현했다. 특정 산식·수치가 특허가 지정한 정답이라는 의미는 아니다. 청구항 6·8의 제공 결과 기반 기준 갱신은 아직 구현하지 않았다.

## 샘플

이름·경력·수량·전승·가격·점수는 전부 가상이다. 실제 생산자의 인증·실적 자료가 아니다. 카탈로그 DB·상품 속성에 저장하지 않는다.

| 가상 상품 | 숙련 | 지역 희소 | 유통 제한 | 역사 | 이야기 | 희소값 | 고격식 결과 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 청자 장인 차도구 | 9 | 9 | 8 | 9 | 8 | 0.86 | 적격, 순위 평가 53 |
| 전통 장류 답례 세트 | 8 | 7 | 7 | 8 | 7 | 0.74 | 적격, 순위 평가 75 |
| 보편 유통 곡물 간식 | 4 | 2 | 2 | 3 | 3 | 0.28 | 제외, 순위 미평가 |

초기 검증 조건은 공식 개막식·기념식 70 + 공식 관계 10 + 공공기관 5 + 감사 답례 0 = 85점이다. 80 이상 구간의 희소 하한 0.70을 적용한다. 간식은 신뢰·실용성이 각각 10이어도 희소 필터에서 제외되므로 순위로 복구되지 않는다.

생일·가족·개인·감사 답례로 바꾸면 25점, 하한 0 구간으로 샘플 3개가 통과한다. 식품을 모든 행사에 추천한다는 뜻은 아니며 기존 행사 금지 속성이 있으면 먼저 제외한다.

## 관리자 사용

- 개발 서버에서 `/admin/formality`를 연다. 기존 관리자 로그인·권한 확인이 적용된다.
- ‘가상 샘플 3개’에서 행사 조건을 바꿔 적격/제외 결과를 확인한다.
- ‘기준표 편집’을 펼쳐 행사 기본점수·보정·구간·희소/순위 가중치를 조정한다.
- 상품 선택 후 5개 속성의 평가값과 자료·출처를 입력한다. 실제 자료를 읽은 사람이 평가값을 정하며 자동 사실 추출·자동 검증은 하지 않는다.
- ‘미입력’과 0점을 구분한다. 실제 근거가 있고 양수 가중치를 쓰는 속성 2개 이상이 필요하다. 근거 변경 시 검수 확인이 해제된다.
- ‘현재 카탈로그’로 전환하면 기존 상품을 읽되 샘플 근거를 옮기지 않는다. 새 v2 근거가 없으면 모두 미검수로 제외되는 것이 정상이다.
- **화면 입력은 메모리에만 있다.** 새로고침/자료 전환 전에 ‘기준·근거 파일로 내보내기’를 사용한다. 파일을 다시 불러올 수 있다. 기존 관리자 화면의 DB 저장과 다르다.
- ‘판정 결과·당시 자료 내보내기’에는 기준·입력·근거·상품/평가 스냅샷이 있어 재현할 수 있다. 이 파일은 근거 파일 가져오기용이 아니며 `evaluateFormality(result.snapshot.catalog, result.snapshot.workspace, result.input)`으로 재계산한다.

별도 DB 저장/게시 기능을 만들지 않은 이유는 상품 검수 전 초안이 고객 추천을 바꾸지 않도록 하기 위해서다. 현재 화면의 버전 이름은 사용자가 붙이는 초안 식별자다. 중앙 정책 이력·게시·승인·동시 수정 제어를 뜻하지 않는다.

## 산식과 제한

- 기존 행사 목표·관계 보정의 10배를 초기 행사 설정으로 이관한다. 새로 추가한 기관 행사 기본값과 발신·목적 보정, 구간표는 검수 전 가안이다.
- 희소값은 `Σ(속성점수 / 10 × 가중치) / Σ(사용한 가중치)`다. 빈 근거·가중치 0·누락 속성은 사용하지 않는다. 2개와 5개로 계산한 결과를 같은 정보량으로 보지 않도록 충족도를 같이 표시한다.
- 희소값은 소수 12자리 정밀도로 확정하고 그 값으로 경계를 비교한다. 화면은 소수 3자리로 표시하지만 판정용 값은 내보낸 결과에 보존된다.
- 순위는 신뢰/10·실용성/10·`1 - 가격/예산`을 사용한 가중평균(0~100)이다. 가격 항목은 예산 안에서 저렴한 상품을 선호하는 초기 정책이다. 예산 미입력 시 가격 가중치를 분모에서도 제외한다.
- 희소값과 행사 격식은 순위 점수에 재가산하지 않는다. 동점은 가격→상품번호로 결정한다. 카테고리 다양성을 우선하고 부족하면 같은 카테고리의 적격 상품으로 채운다.
- ‘실속·표준·격식’의 완성 세트 3안은 아직 아니다. 현재는 적격 상위 최대 3개다. 포장 구성·완성 가격·실물 검수 후 역할별 선택 규칙을 추가해야 한다.
- 총액 표시는 상품대만이다. 배송·포장·세금 조정 견적, 법령 가액 판정, 납기 확약을 제공하지 않는다.
- 판단 파일은 공식 결재 문서나 서명된 검수 기록이 아니다. 기준·근거가 같아도 현재 카탈로그가 달라지면 결과가 달라질 수 있으므로 과거 결과를 재현할 때는 포함된 스냅샷을 사용한다.

## 호출과 검증

`src/engine/eligibility.ts`는 서버·브라우저·CLI에서 같은 함수를 사용할 수 있다. 기존 `recommend()`를 교체하지 않았으며 기존 결과 카드·공유·제작 코드와 형태를 혼동하지 않도록 별도 결과 타입을 사용한다.

```
npm run formality:sample
npm run formality:sample -- --json
node --test test/eligibility.test.ts
node scripts/e2e/formality.mjs
```

화면 검증에는 `ONDAP_DATA_SOURCE=local`인 개발 서버가 필요하다. 새 화면 검증은 상품·접수 파일을 변경하지 않는다. 전체 검증 실행기에도 `formality` 묶음을 등록했다.

정책 형식·숫자 범위·구간 정합성·중복 상품·근거 길이·수량·예산을 검증한다. UI 파일 가져오기는 2MB까지이고 현재 카탈로그에 없는 상품번호를 거절한다. React 텍스트로만 근거를 표시하고 입력 URL을 자동 실행하지 않는다.

배포 전 코드 검증과 별개로, 운영 전환에는 실제 상품 검수·행사 전문가 검수·정책 저장/게시·전체 호출 경로 이관이 필요하다. 현재 DB 스키마와 백업 형식은 변경하지 않았다.

2026-10-28 검증: 전체 단위 테스트 140개(신규 엔진 11개 포함), 타입 검사, 운영 빌드 통과. 관리자 브라우저 검증은 고격식 2개/저격식 3개, 검수 해제, 파일 왕복·손상 거절, 결과 스냅샷, 실상품 분리, 모바일 입력과 콘솔 오류를 확인했다. 실제 상품 근거·점수 교정과 운영 DB·납품 검증은 수행하지 않았다.
