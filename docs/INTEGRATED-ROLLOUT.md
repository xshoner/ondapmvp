# 통합 개선 배포·운영 점검표

대상: OD-06, OD-08, OD-13, OD-30, OD-19, OD-20, OD-21, OD-26.

## 적용 원칙과 남은 선행 조건

이 브랜치는 기존 상품·추천·포장·접수·인쇄·관리자 흐름을 유지하며 추가 변경을 한다. DB 변경을 되돌리거나 운영 데이터를 초기화할 필요가 없다.

- **OD-06:** 포장 없는 추천도 수량을 전달한다. 코드는 상품별로 보관하며, 같은 상품에 여러 옵션 행/여러 디자인이 있으면 자동 매칭하지 않는다. 정확한 옵션·주문 항목별 완전 자동 매칭에는 OD-09의 카페24 주문 항목 API 연결이 선행되어야 한다. 이번 변경은 모호한 상태에서 잘못된 코드를 입력하지 않는 수동 확인 경로를 제공한다. 옵션을 임의로 선택하지 않는다.
- **OD-13:** 편집기의 감사 답례/축하·위로 목적은 이번에 구분한다. 전체 추천 엔진의 목적 모델(OD-02), 실제 상품과 포장 규격의 검수(OD-07)는 별개다. 미확인 목적의 기존 이미지·문구는 추천 기본값으로 쓰지 않고 ‘다른 이미지/문구’에서 고객이 직접 고를 수 있다. 기존 디자인을 복원하면 편집 내용을 유지한다.
- **OD-08/21/30/26:** 새 DB 함수/컬럼이 필요하므로 **DB 변경을 먼저 적용하고 앱을 배포**한다. 구 DB를 연결하면 상품 갱신·의견 저장·전체 통계는 실패를 알리고, 기존 데이터를 파괴하거나 부분 합계를 정상 실적으로 표시하지 않는다. 고객 추천·코드 조회 등 기존 읽기 기능은 유지된다.
- 예약 실행과 지속 운영 기록에는 서버 전용 키가 필요하다. 키가 없으면 구조화된 서버 콘솔 기록은 남고, 관리자 운영 상태에 미설정으로 표시한다.
- 운영 SQL 실행과 카페24 스킨 수정은 기존 저장소 규칙대로 운영 담당자가 수행한다. 이 문서의 절차를 코드 구현 또는 로컬 검증과 혼동하지 않는다.

## 1. DB 변경

1. 운영 DB의 기존 백업/복구 지점을 확인한다. 이미 적용된 20261020~20261026 변경을 다시 실행하지 않는다.
2. 새 파일 `supabase/migrations/20261027000000_integrated_improvements.sql`만 검토해 SQL Editor에서 실행한다. **기존 운영 DB에 setup.sql을 실행하지 않는다.**
3. 아래 읽기 전용 점검을 실행한다. 함수 5개, 추가 컬럼 4개, 운영 기록 테이블과 RLS를 확인한다.

```sql
select proname from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and proname in
('submit_feedback','sync_product_snapshot','admin_stats','operational_health','export_application_snapshot');
select table_name,column_name from information_schema.columns
where table_schema='public' and ((table_name='recommendation_feedback' and column_name='request_id')
or (table_name in ('packaging_styles','design_images','design_texts') and column_name='targeting'));
select relrowsecurity from pg_class where oid='public.operation_events'::regclass;
```

새 시험 프로젝트는 기존과 같이 `npm run db:setup-sql`로 생성한 setup.sql 전체를 실행한다. 같은 버전의 소스·DB를 사용한다.

## 2. 배포 환경

- 기존 Supabase·카페24 환경변수는 유지한다.
- `SUPABASE_SERVICE_ROLE_KEY`: 서버 전용 Sensitive 변수. NEXT_PUBLIC_ 접두어를 붙이지 않고 고객 코드나 스킨에 넣지 않는다. 일반 고객/관리자 데이터 요청은 계속 기존 RLS 클라이언트를 사용한다.
- `CRON_SECRET`: 32자 이상 무작위 값. Vercel Cron이 Authorization 헤더로 전달한다. URL·로그·보고서에 값을 적지 않는다.
- 이 값들은 운영 환경에 설정하고, 실제 운영 데이터를 변경하는 예약 작업을 시험 배포에서 실행하지 않는다.
- `vercel.json`의 예약은 상품 동기화 UTC 21:00(한국 06:00), 의존 서비스 점검 UTC 22:15(한국 07:15)이다. 플랫폼의 실제 실행 시각과 플랜 제한도 확인한다. 별도의 실시간 변경 알림은 이번에 설치하지 않았다.
- 웹훅/슬랙/메일 수신자를 임의로 추가하지 않았다. Vercel의 실패 경보 또는 외부 모니터를 담당자와 연결해야 실제 장애 알림을 받을 수 있다.

참고: [Vercel 예약 인증](https://vercel.com/docs/cron-jobs/manage-cron-jobs), [Next 응답 후 작업](https://nextjs.org/docs/app/api-reference/functions/after), [카페24 전체 상품 수 조회](https://apidocs.cafe24.com/en/docs/2026-06-01/front/get-products-count).

## 4. 관찰과 오류 대응

서버 기록:

- `kind=ondap_operation`: 정해진 작업명, 성공/오류, 짧은 오류 분류, 소요시간. 요청 본문·디자인 코드·이름·사진·토큰·원문 오류는 넣지 않는다.
- `kind=ondap_web_vital`: 고객 첫 화면/추천/편집기 구분, LCP/INP/CLS 수치만 수집. 전체 URL·쿼리·기기 식별자는 받지 않는다. 이 공개 지표는 운영 참고용이며 외부에서 위조할 수 있는 값을 거래 실적에 사용하지 않는다.
- 운영 기록은 DB에서 90일, 로컬 시험 파일에서 최근 500건을 보관한다. 최근 50건 표시와 24시간 전체 오류 수는 구분한다.
- 정상 상품 동기화 때 90일 이전 운영 기록을 정리한다. 고객 접수·인쇄 원본은 이 정리 작업이 삭제하지 않는다.

외부 환경에서 다음 읽기 전용 명령을 스케줄러로 실행할 수 있다. `CRON_SECRET`은 환경변수로만 전달한다. 하나라도 실패하거나 의존 서비스 인증이 미설정이면 종료 코드 1이다. 출력에는 인증값을 넣지 않는다.

```powershell
npm run ops:check -- https://운영주소
```

오류 대응 순서: 운영 상태/콘솔 확인 → DB 버전·연결 확인 → 예약 실행/최근 갱신 확인 → 카페24 권한/전체 상품 수 확인 → 접수/파일/인쇄 원본 확인. 실패가 감춰진 기능을 ‘정상’으로 판단하지 않는다. 상품 동기화 실패 시 직전 정상 목록을 유지하며 36시간 갱신 지연을 상태 점검에서 실패로 알린다.

## 5. 백업과 시험 복구

### 범위

`ops:backup`은 애플리케이션 표 11개를 DB의 한 읽기 스냅샷으로 가져오고, 참조된 비공개 인쇄 PNG와 업로드된 포장/추천 이미지를 함께 저장한다. 파일은 SHA-256과 길이를 기록한다. 재주문이 참조하는 원본 접수도 포함한다. **Supabase 인증 사용자·비밀키·관리자 계정·플랫폼 설정의 백업을 대체하지 않는다.** 이 항목은 Supabase 자체 DB/인증 백업과 운영 계정 절차로 별도 확보한다. 저장소 밖 정적 이미지·글꼴은 같은 커밋의 소스/배포 자산으로 복구한다.

백업에는 고객 디자인과 이력이 있으므로 접근이 제한된 저장소에 보관한다. 백업 폴더는 git에서 제외되어 있으며 기존 폴더를 덮어쓰지 않는다. 다운로드 중 하나라도 실패해 manifest가 없으면 미완료 백업이다.

```powershell
npm run ops:backup -- backups/새백업이름
npm run ops:verify-backup -- backups/새백업이름 https://새시험프로젝트주소
```

두 번째 명령은 네트워크/운영 DB에 쓰지 않고 파일 무결성·참조를 확인한 뒤 `restore-staging.sql`만 만든다. 새 프로젝트 주소를 주면 저장소 공개 URL도 그 프로젝트로 바꾼다. 같은 폴더에 이미 복구 SQL이 있으면 덮어쓰지 않는다.

### 시험 복구 절차

1. 운영과 분리된 새 Supabase 시험 프로젝트에 같은 커밋의 setup.sql을 적용한다.
2. 인증 백업에서 참조된 사용자 ID를 준비한다. 원래 사용자 ID가 없으면 외래키 검사가 복구를 거절하며 전체 트랜잭션이 취소된다. 임의로 외래키 검사를 끄지 않는다.
3. 생성된 SQL의 대상이 시험 프로젝트인지 검토한 뒤 실행한다. SQL은 애플리케이션 표를 교체하므로 **운영 프로젝트에서 실행하지 않는다.** 트리거를 트랜잭션 안에서만 중지/복구해 원래 시각·상태·변경 이력을 보존한다.
4. `files/design-files/`와 `files/packaging-assets/`의 파일을 manifest의 버킷·상대 경로대로 시험 프로젝트 Storage에 복구한다. design-files는 비공개를 유지한다. 업로드는 담당자가 대상 프로젝트를 확인한 뒤 수행한다.
5. 접수 수량, 재주문 원본, 상태 조회, 비공개 원본 다운로드, 인쇄 PDF·QR, 포장 이미지, 추천·통계를 대조한다. 실제 프린터/재단기 출력은 별도로 확인한다.
6. 복구 시간과 실패 지점을 기록해 다시 시험한다. 로컬 DB 복구 시험만으로 실제 클라우드·인증·Storage 복구가 완료됐다고 판단하지 않는다.

## 6. 되돌리기

문제가 있으면 이전 앱 배포로 복구한다. 이번 DB 변경은 추가 컬럼/표/함수이므로 그대로 둬도 이전 앱과 호환된다. 사고 중에 운영 DB에서 컬럼·표를 삭제하지 않는다. 예약 작업도 이전 vercel.json으로 복구되는지 확인한다. 이미 저장된 접수·인쇄 파일은 유지한다.

OD-19의 캐시는 요청 범위만 사용하므로 별도 전역 캐시 초기화는 필요 없다. 추천 기록의 응답 후 저장은 실패 시 운영 기록에 남고 고객 결과 응답을 막지 않지만, 플랫폼 강제 종료까지 보장하는 영속 대기열은 아니다. 트래픽과 기록 중요도가 커지면 별도 영속 작업 대기열로 확장한다.
